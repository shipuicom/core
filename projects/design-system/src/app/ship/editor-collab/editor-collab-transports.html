Writing your own transport

A transport is four members — anything that delivers messages in order per sender qualifies (WebRTC data channels, SSE + POST, a message broker):

  • send — deliver the message to every other peer on the document. Echoing it back to the sender is harmless (the session drops its own clientId ), just wasteful. Queue while disconnected; the session never retries.
  • subscribe — call back with every message from other peers, in the order each peer sent them. Return the unsubscribe function; the session calls it on detach.
  • connected — a signal, read once at attach into ShipEditorCollab.connected . Informational only; no message is gated on it.
  • destroy — optional. shCollab calls it only on transports it created from a string; a transport you bind yourself is yours to destroy.

Ordering is the one hard requirement. Per-sender order is enough for two peers. For three or more, route through something that serializes all senders into one arrival order (a relay, a broker topic, a single server) — that total order is what every peer rebases against.
